# РНБ WarDogs — Discord bot

Автоматизация Discord-сервера клана «РНБ» (WarDogs). Фаза 1: провижининг
структуры сервера одной командой.

## Установка

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
```

Заполни `.env`:

* `DISCORD_BOT_TOKEN` — токен бота из Discord Developer Portal.
* `DISCORD_GUILD_ID` — (опционально, для разработки) ID тестового сервера,
  чтобы slash-команды синхронизировались мгновенно, а не до часа.

### Чек-лист перед первым запуском (Фаза 0)

* [ ] Создано приложение и бот в Discord Developer Portal
* [ ] Бот приглашён на сервер с правами: Manage Channels, Manage Roles,
      Send Messages, Embed Links, Attach Files, Use Application Commands
* [ ] Роль бота в списке ролей сервера — ВЫШЕ всех ролей, которые он
      создаёт/раздаёт (иначе `create_role`/`create_channel` с overwrites
      будут падать с `Forbidden`)
* [ ] Токен лежит в `.env`, `.env` не закоммичен
* [ ] В Developer Portal → Bot включён привилегированный интент **Message
      Content Intent** (нужен для команды `!tr` — иначе бот не увидит текст
      сообщений)

## Запуск

```bash
python bot/main.py
```

## Команды

### `/setup-server`

Доступна только владельцу/администратору сервера. Читает
`bot/config/server_structure.yaml` и идемпотентно создаёт недостающие роли,
категории и каналы (с permission overwrites для каналов с `restricted_to`).
Повторный запуск ничего не дублирует — в конце присылает embed-отчёт: что
создано, что уже было, что не удалось (например, не хватило прав).

Имена каналов в конфиге не обязательно писать заранее в "дефисном" виде —
`_shared.normalize_channel_name()` (нижний регистр, пробелы → дефисы)
применяется и при создании, и при проверке "уже существует", и в
`/sync-server`, так что предсказанное имя всегда совпадает с тем, что реально
присвоит Discord (категорий это не касается — их Discord не нормализует).

Конфиг можно редактировать и дополнять — при следующем запуске команда
добьёт недостающее. **Никогда ничего не удаляет** — для удаления того, что
пропало из конфига, см. `/sync-server` ниже.

**Права категорий — исключение из «никогда не трогает существующее»**: если
у категории в `categories[].restricted_to` (тот же формат, что у каналов)
задан список ролей — `/setup-server` синхронизирует overwrites категории при
КАЖДОМ запуске, даже если категория уже существовала. Иначе правка
`restricted_to` в конфиге никогда бы не долетала до уже созданных на сервере
категорий — команда бы просто молча продолжала игнорировать расхождение.
Каналы так не работают (у них создание по-прежнему одноразовое, права не
пересинхронизируются) — сознательная асимметрия, не баг.

Сейчас в конфиге все категории, кроме `📜 НАЧАЛО / START HERE`, закрыты от
`@everyone` и открыты только по `restricted_to` — новый участник видит
только `правила-verification`, пока не выберет отряд через `/post-onboarding`
(получение отрядной/ранговой роли открывает всё остальное, кроме
`🔒 ШТАБ ОФИЦЕРОВ`, куда нужна отдельная офицерская роль).

### `/sync-server`

Доступ — **уже, чем у `/report`/`/start-op`**: только Офицер или Верховный
Главнокомандующий (`sync.allowed_roles` в конфиге), не Глава отряда. Причина
— это единственная команда бота, которая **удаляет** данные с сервера.

Защита в два независимых слоя, не один самодельный `if`:
1. **Discord-нативный барьер**: команда объявлена с
   `@app_commands.default_permissions(manage_guild=True)` — по умолчанию
   Discord вообще не даёт открыть/вызвать эту команду тем, у кого на сервере
   нет права **Manage Server** (Управление сервером). Это проверяется на
   стороне Discord, до того как наш код вообще получит interaction.
2. **Проверка роли в коде** (`_shared.has_access` + `sync.allowed_roles`) —
   второй, независимый слой поверх первого.

> **Ручной шаг, не часть `/setup-server`**: `default_permissions` — это
> только *подсказка* Discord'а по умолчанию, а не автоматическая выдача прав
> ролям. Чтобы Офицер и ВГК реально могли вызвать `/sync-server`, зайди в
> Настройки сервера → Роли → (роль) → включи **Manage Server**, для обеих
> ролей. Это открывает всей роли широкое право на уровне всего Discord-сервера
> (не только для этой команды) — соизмеримо с тем, что `/sync-server`
> необратимо удаляет данные. Глава отряда (`Squad Lead`) сюда намеренно **не**
> включён — это уже, чем доступ к `/report`/`/start-op`, при желании дать
> Squad Lead доступ надо синхронно поменять и `sync.allowed_roles` в конфиге,
> и список ролей с Manage Server в Discord — иначе два слоя защиты разъедутся.

Сканирует **весь сервер целиком** — `guild.roles` и `guild.channels`
полностью, а не только то, что перечислено в `server_structure.yaml`:
* роль — кандидат на удаление, если её нет в `roles` конфига (исключения:
  `@everyone` и managed-роли — интеграции, роль самого бота);
* категория — кандидат, если её нет в `categories` конфига (удаляется вместе
  со всеми каналами внутри);
* канал внутри известной категории — кандидат, если его нет в списке
  `channels` этой категории в конфиге;
* **канал вообще без категории** (например случайно оставшийся Discord'ом
  по умолчанию `general`) — тоже кандидат, эта ветка не привязана к yaml
  вообще.

Категории с `dynamic: true` (`🎯 АКТИВНЫЕ ОПЕРАЦИИ`) — исключение: их
содержимое никогда не сканируется, им управляет `/start-op`.

Ничего не удаляется молча: перед удалением бот присылает список всех
кандидатов и ждёт подтверждения кнопкой (60 сек, потом отмена по таймауту).
После подтверждения — необратимо удаляет и присылает итог (удалено/не
удалось).

### `/report`

Доступна Главе отряда, Офицеру, Верховному Главнокомандующему или админу —
список ролей берётся напрямую из `restricted_to` канала `report.channel`
(`карта-и-счёт`) в `server_structure.yaml`, так что права канала (Фаза 1) и
проверка роли в коде используют один и тот же источник правды. Остальным
(«Боец» и ниже) команда вежливо отказывает.

Поля: `map`, `score_blue`, `score_other`, `status` (в процессе/победа/
поражение), `squads_present`, `pincered` (да/нет — зажаты между двумя
фронтами), `screenshot` (опционально).

При отправке:
* постит embed в канал `карта-и-счёт`;
* добавляет строку в `bot/data/match_log.csv` (timestamp, автор, все поля
  формы, источник — `manual`/`rcon` из конфига). Файл создаётся автоматически
  при первой отправке и не коммитится.

> Точный шаблон embed'а из `rnb-plan.md` п.2.4 не был доступен при
> реализации — сделан собственный разумный вариант (цвет по статусу, счёт,
> отряды, предупреждение при "зажаты"). Пришли реальный шаблон, если он
> отличается, — подгоним один в один.

### `!tr <текст>`

Текстовая команда (не slash), доступна всем. Автоматически определяет
направление перевода: если в тексте есть кириллица — RU→EN, иначе EN→RU.
Отвечает переводом в том же канале (reply, без лишнего пинга). Перевод — через
`deep-translator` (Google Translate без официального ключа/квоты API).

#### Зеркалирование RU↔EN-каналов (опционально, выключено по умолчанию)

В `server_structure.yaml` есть секция:

```yaml
translate:
  mirror_pairs_enabled: false
  mirror_pairs:
    - {ru_channel: "объявления-announcements", en_channel: "..."}
```

Если включить `mirror_pairs_enabled: true` и заполнить пары каналов —
каждое обычное сообщение в `ru_channel` будет переведено и продублировано в
`en_channel` через webhook, подписанным именем и аватаркой автора. Свои же
переведённые сообщения бот не зеркалит повторно (проверка по `webhook_id`).
Webhook (`РНБ Translate Mirror`) создаётся автоматически при первом
срабатывании в целевом канале — боту нужны права Manage Webhooks.

### `/start-op` и `/end-op`

Доступ — тот же уровень, что и у `/report` (Глава отряда/Офицер/ВГК/админ).

В игре у отряда уже есть свой приватный голосовой канал прямо в матче (Esc →
Create/Join Squad) — Discord не дублирует его во время боя. `/start-op`
закрывает то, что игра не даёт: координацию **до** и **после** операции.

`/start-op` (параметры: `server` — **обязательный**, свободный текст,
регион+номер игрового сервера, например `EU 3`; `squad` — выбор отряда,
опционально; `map`, `note` — текст, опционально):
* создаёт временную пару каналов (текст + голос) в категории
  `ops.temp_category` (`🎯 АКТИВНЫЕ ОПЕРАЦИИ`) с одинаковым именем
  `операция-{отряд}-{id}` — это и есть механизм связи пары без глобального
  состояния, переживает рестарт бота;
* постит анонс-embed в `ops.announce_channel` (`сбор-на-операцию`) — сервер,
  отряд (с упоминанием его роли, если выбран), карта, заметка, ссылки на
  каналы, и кнопка **✅ Иду** (см. ниже);
* каналы открыты всем — цель собрать людей на операцию, не спрятать их.

Кнопка **✅ Иду** под анонсом — persistent (`custom_id`, `timeout=None`,
переживает рестарт бота: регистрируется заново в `Ops.__init__` при каждом
старте) и работает как **toggle**: клик добавляет упоминание нажавшего в поле
«Участники» прямо в embed анонса, повторный клик тем же человеком — убирает
его оттуда (поле возвращается к «—», если список опустел). Без отдельного
in-memory состояния — список участников читается и переписывается из
текущего embed'а самого сообщения, так что рестарт бота ничего не теряет.

Автоочистка: раз в `ops.cleanup_delay_seconds` (по умолчанию 300 — 5 минут)
бот проверяет, пуст ли голосовой канал операции; как только да — удаляет оба
канала пары. Если бот перезапускался во время активной операции — на старте
(`on_ready`) он сам находит незавершённые пары каналов в
`ops.temp_category` и возобновляет слежку **с полной задержки заново** (не
"оставшееся время") — это упрощение, не точный resume; проверено на реальном
сервере (см. историю коммитов), что таймер при этом не задваивается и не
удаляет раньше срока.

`/end-op` — досрочно завершить операцию. Запускать **внутри её текстового
канала** — удаляет пару немедленно, не дожидаясь таймера.

> Старые статичные отрядные текстовые каналы (штурм/логистика/...) и
> голосовой-триггер «➕ Создать голосовой» убраны из
> `server_structure.yaml` — они не были ничем наполнены и не несли функции
> (задумывался Join-to-Create, но не был реализован). Роли отрядов остались
> — как метка специализации и для пинга в анонсе `/start-op`. Если такие
> каналы уже были созданы на сервере первым запуском `/setup-server` до
> этого изменения — удали их вручную, бот сам ничего не удаляет (только
> досоздаёт недостающее по конфигу).

### `/post-onboarding`

Доступ — Officer+ (тот же список ролей, что у `/sync-server`,
`sync.allowed_roles`). Постит/обновляет **два** закреплённых сообщения:

1. В `#правила-verification` — приветствие с 5 кнопками отрядов (Штурм/
   Логистика/Разведка/Транспорт/Поддержка), persistent view (переживает
   рестарт бота). Языковых кнопок нет — роли RU/EN убраны.
2. В `#сбор-на-операцию` — explainer для пустого состояния (кто постит
   операции, что делать, если сейчас пусто, что сервер объявляется в каждом
   анонсе отдельно).

Обе публикации — через `_replace_pinned_by()`: перед постом ищет своё
предыдущее закреплённое сообщение в канале (по заголовку embed'а) и
заменяет его, а не плодит дубликаты при повторном запуске команды.

По клику на кнопку отряда: снимает предыдущую отрядную роль, если была,
выдаёт новую + роль «Новобранец | Recruit», если её ещё не было. Ответ —
ephemeral-сообщение с текстом **и настоящей кнопкой-ссылкой**
(`discord.ButtonStyle.link`, `url=` реальный `jump_url` канала) на
`#сбор-на-операцию` — не текстовое упоминание, кликабельный переход. Ошибка
прав (роль бота не выше ролей отрядов) — понятное ephemeral-сообщение, не
тихий сбой.

Замена Carl-bot/reaction-roles для выбора отряда — ничего внешнего подключать
не нужно.

### `/stats`

Доступ — тот же уровень, что у `/report` (данные оттуда же). Только читает
`bot/data/match_log.csv` — новых данных не собирает. Показывает: всего
операций, счёт побед/поражений/в процессе, сколько раз отмечен «зажим»
(pincered) и в каком проценте матчей, разбивку побед/поражений по каждой
карте. Если лога ещё нет — вежливое ephemeral-сообщение вместо ошибки.

## Структура

```
bot/
  main.py              # точка входа, загрузка cogs, синхронизация команд
  cogs/
    _shared.py           # общие хелперы: конфиг, доступ по ролям, список отрядов
    provisioning.py     # /setup-server, /sync-server
    report.py            # /report
    translate.py         # !tr + опциональное зеркалирование каналов
    ops.py                # /start-op, /end-op
    onboarding.py         # /post-onboarding (кнопки выбора отряда)
    stats.py              # /stats
  config/
    server_structure.yaml
  data/                 # создаётся кодом; не коммитится (см. .gitignore)
```
